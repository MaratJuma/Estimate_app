# Контекст проекта

## Общая идея

Проект — это внутренняя рабочая система для управления:

- поставщиками
- услугами
- сметами
- позициями смет по дням

Интерфейс ориентирован не на “витринную красоту”, а на:

- стабильность
- предсказуемость
- быстрый доступ к связанным сущностям
- сохранение пользовательского контекста
- минимизацию “прыжков” интерфейса

---

# Текущая архитектура

## Основные сущности

### Contractor
Поставщик.

Хранит:
- название
- категорию
- контактные данные
- комментарий

Связан с услугами:
- один поставщик → много услуг

---

### Service
Услуга поставщика.

Хранит:
- название
- поставщика
- себестоимость
- цену клиенту
- описание / комментарий
- медиа-ссылку
- флаг активности

Используется:
- в каталоге услуг
- в позициях смет

---

### Estimate
Смета.

Хранит:
- клиента
- менеджера
- комментарий
- дату создания
- статус утверждения

Связана:
- со днями сметы
- через дни — с позициями сметы

---

### EstimateDay
День внутри сметы.

Хранит:
- номер дня
- заголовок / описание дня

Связан:
- со сметой
- с позициями дня

---

### EstimateItem
Позиция сметы.

Хранит:
- ссылку на услугу
- количество
- цены
- производные суммы
- дополнительные комментарии

Используется для формирования полной сметы.

---

# Текущие представления и логика

## Списки
Есть основные list-view:

- `service_list`
- `contractor_list`
- `estimate_list`

И дополнительный список выбора услуг в контексте сметы:

- `estimate_item_create`

Особенности:
- поиск
- фильтрация
- пагинация
- сохранение query-параметров между страницами
- ссылки в detail с сохранением контекста через `next`

---

## Карточки
Есть detail-view для ключевых сущностей:

- `contractor_detail`
- `service_detail`
- `estimate_detail`

Карточка:
- показывает полную информацию по объекту
- выступает “центром действий” по сущности
- хранит контекст возврата в список через `next`

---

## Формы
Формы используются для:

- создания
- редактирования
- создания связанной сущности из карточки

Примеры:
- `contractor_update`
- `service_create`
- `service_create_for_contractor`
- формы редактирования / создания элементов сметы

---

# Принципы UI

## 1. Список — для обзора
Список должен быть лёгким и не перегруженным действиями.

Подход:
- в таблице оставляем только ключевое действие “Открыть” или переход по названию
- дополнительные действия переносим в карточку

Пример:
- в списке смет в колонке “Действия” оставлена только кнопка “Открыть”
- действия `редактировать`, `утвердить`, `дублировать` находятся уже в карточке сметы

---

## 2. Карточка — для действий
Карточка объекта является основной точкой управления.

Например карточка поставщика:
- просмотр информации
- переход к редактированию
- добавление услуги
- просмотр связанных услуг
- возврат в исходный список

---

## 3. Формы — без потери контекста
Пользователь не должен “теряться” после редактирования.

Логика возврата:
- список → карточка
- карточка → форма
- форма → назад в карточку
- карточка → назад в список

Это реализуется через `next`-контекст.

---

## 4. Стабильность важнее декоративности
Для интерфейса выбран принцип “рабочей панели”:

- таблицы должны быть стабильны по ширине
- пагинация не должна смещаться
- основные элементы должны оставаться на своих местах
- допустим горизонтальный скролл, если это сохраняет структуру

---

# Реализованные улучшения

## 1. Упрощение списка смет
В колонке действий оставлена только кнопка:

- `Открыть`

Действия:
- `Редактировать`
- `Утвердить`
- `Дублировать`

перенесены / сосредоточены в карточке сметы.

---

## 2. Добавление кнопки “Дублировать”
В шаблон карточки / редактирования сметы добавлена кнопка:

- `Дублировать`

Логика:
- дублирование рассматривается как отдельное действие над сметой
- действие доступно из карточки, а не из общего списка

---

## 3. Стабилизация таблиц
Для основных таблиц внедрён подход:

- `table-layout: fixed`
- фиксированная ширина таблицы
- контролируемый перенос длинного текста
- обёртка с `overflow-x: auto`

Цель:
- исключить изменение ширины столбцов между страницами пагинации
- сохранить визуальный контекст

---

## 4. Стабилизация пагинации
Пагинация переработана:

- зафиксированы кнопки `[<<] [<] [>] [>>]`
- числовые кнопки переведены на фиксированные слоты
- убрана “пляска” элементов при переходах
- логика пагинации вынесена в helper `build_pagination_slots(page_obj)`

Используется единый partial:
- `pagination.html`

---

## 5. Добавление пагинации в выбор услуг для сметы
В `estimate_item_create` и `estimate_item_form.html` добавлена пагинация списка услуг.

Это важно, потому что:
- каталог услуг может быть большим
- выбор услуги для позиции сметы должен быть управляемым
- фильтры и поиск должны сохраняться между страницами

---

## 6. Унификация `next`-контекста
Введён рабочий стандарт навигации через `next`.

Основная схема:

- из списка в карточку передаётся `current_full_path`
- карточка хранит `next_url`
- карточка строит `detail_return_url`
- из карточки в форму передаётся `detail_return_url`
- форма по кнопке “назад” и после сохранения возвращает на `next_url`

Это позволило устранить ошибки навигации, когда форма перескакивала через карточку сразу в список.
